[[section-design-decisions]]
== Architekturentscheidungen

=== 1: Auth0 statt eigener Authentifizierung

*Kontext*: Das System benötigt Authentifizierung und rollenbasierte Authorisierung für Admin (CTO/Tech-Lead)- und Mitarbeiter-Zugriff.

*Entscheidung*: Nutzung von Auth0 als externem Identity Provider statt eigener User-Verwaltung.

*Begründung*:

* Keine Implementierung eigener Passwort-Hashing/Speicherung nötig (Security-Risiko minimiert)
* OAuth2/OIDC-Standard bereits etabliert, gute Libraries verfügbar
* Integriertes Audit-Logging für Login-Events (Qualitätsanforderung)
* Schnelle Integration via `@auth0/auth0-angular` und `passport-jwt`
* Kostenloser Tier

*Konsequenzen*:

Pros::
* Weniger Code
* Relativ einfaches Setup

Cons::
* Abhängigkeit von externem Service (Auth0 muss erreichbar sein)
* Custom Claims für Rollen müssen in Auth0 konfiguriert werden

'''

=== 2: MongoDB statt relationale Datenbank

*Kontext*: Datenmodell für Technologien in lokaler Entwicklungsumgebung.

*Entscheidung*: MongoDB (NoSQL, dokumentenbasiert) als Docker-Container statt SQL-Datenbank.

*Begründung*:

* Flexible Schema-Evolution (neue Felder können einfach hinzugefügt werden)
* JSON-ähnliche Dokumente passen gut zu TypeScript-Objekten
* Mongoose bietet typsicheres Schema + Validierung in TypeScript
* Einfaches lokales Setup via Docker Compose (keine manuelle Installation nötig)
* Automatisches Seeding via `init-mongo.js` beim ersten Start
* Keine komplexen Joins/Transaktionen nötig

*Konsequenzen*:

Pros::
* Schnellere iterative Entwicklung
* Einfache Integration mit NestJS via Mongoose
* Reproduzierbare Entwicklungsumgebung (Docker)
* Daten-Persistierung via Docker Volume

Cons::
* Keine referentielle Integrität auf DB-Ebene

'''

=== 3: Signals statt RxJS für Client-State

*Kontext*: Angular bietet sowohl RxJS Observables als auch Signals für reaktives State-Management.

*Entscheidung*: Signals als primärer State-Mechanismus im `TechnologyService`.

*Begründung*:

* Signals sind Angular 16+ Standard für reaktive State-Verwaltung
* Einfachere API als RxJS (weniger Boilerplate, kein manuelles Unsubscribe)
* Automatische Change Detection
* Computed Signals für abgeleiteten State (z.B. gefilterte Technologien)

*Konsequenzen*:

Pros::
* Weniger Code, bessere Lesbarkeit
* Automatisches Subscription-Management
* Zukunftssicher (Angular-Direction)

'''

=== 4: Conditional Validation statt separater Entwurf-Entität

*Kontext*: Technologien sollen als Entwurf gespeichert werden können (ohne vollständige Pflichtfelder), bevor sie publiziert werden.

*Entscheidung*: Ein `Technology`-Schema mit `isPublished`-Flag und conditional validation, statt separate Entitäten für Entwürfe und publizierte Technologien.

*Begründung*:

* Einfacheres Datenmodell (eine Collection statt zwei)
* Custom Validator `@IsRequiredWhenPublished` prüft Pflichtfelder nur bei `isPublished=true`
* Publizieren = simples Update (`isPublished: false → true`)
* Kein Daten-Migration zwischen Collections nötig

*Konsequenzen*:

Pros::
* Weniger Komplexität in Datenmodell und Queries
* Einfacher Workflow für Admins (Entwurf → Publish in einem Formular)

Cons::
* Validation-Logik etwas komplexer (sowohl im Frontend als auch Backend)

'''

=== 5: SVG-Radar statt Canvas/Charting-Library

*Kontext*: Visualisierung der Technologien als Radar mit Quadranten und Ringen.

*Entscheidung*: Manuelle SVG-Generierung statt Charting-Library (z.B. D3.js, Chart.js).

*Begründung*:

* Volle Kontrolle über Layout und Interaktivität
* Keine zusätzliche Library-Abhängigkeit
* SVG ist responsive und skaliert automatisch
* Halbwegs einfache Positionierungs-Logik
* TypeScript-Berechnung der Punkt-Positionen transparent und wartbar

*Konsequenzen*:

Pros::
* Leichtgewichtig, kein Library-Overhead
* Anpassbar (z.B. Farben, Tooltips, Click-Events)

Cons::
* Mehr eigener Code für Positionierung/Rendering
